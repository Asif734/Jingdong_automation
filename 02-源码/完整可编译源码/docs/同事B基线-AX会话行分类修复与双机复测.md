## 原问题

部分千牛/macOS 组合会在真实客户行之前或客户分组之间暴露一个空白 `AXGroup`：

- 空白分组栏：高度约 34 px，没有 UID、昵称或其他文字；
- 真实客户行：高度约 52 px，标题中可取得 UID 或昵称。

旧代码仅按角色、位置、宽高范围判断“像不像客户行”，所以会把 34 px 的分组栏也加入客户候选。后续身份读取持续失败，造成重复重试或正常客户迟迟不能进入任务表。

这不是 M1/M2 芯片能力差异。直接原因是不同千牛版本、macOS 版本、账号列表状态组合产生了不同的 AX 树形结构。

## 新分类算法

程序先在每一个左侧会话容器内收集几何位置合理的直接子节点，再分三类：

1. `customer`：能取得完整 UID、可用昵称或可靠截断前缀；正常进入红点扫描。
2. `groupHeader`：节点自身没有任何身份文字，并且高度不超过同一容器内真实客户行中位高度的 80%；直接忽略，即使其区域碰巧出现红色像素，也不会创建客户任务。
3. `unknown`：暂时没有身份，但高度与真实客户行相近；继续保留在原有的有限身份确认流程中，避免误删真实客户。

额外边界：

- 如果当前画面完全没有一条可用于计算正常高度的已识别客户行，程序不会武断删除空白节点，而是保留为 `unknown`。
- 中文、英文、淘宝内部 UID 均沿用同事 B 基线的身份规则。
- 当前正在查看的客户没有特殊排除规则；只要画面存在红点，仍参与扫描。
- 一个异常节点不会让其后的正常客户消失。

## 在同事电脑上的复测步骤

1. 先停止并退出旧自动客服，千牛保持登录和在线。
2. 备份旧 App；不要同时运行两个自动客服 App。
3. 将候选 App 复制到 `/Applications`。若覆盖同 bundle ID 的旧候选版，先保留旧 App 作为回滚。
4. 首次打开时检查“辅助功能”和“屏幕录制”；macOS 若重新取消授权，重新打开对应权限。
5. 千牛只保留一个明确的接待中心窗口，打开“正在接待”列表。
6. 在自动客服里填写本机真实客服名称，然后等待 OCR 和 V2 显示就绪。
7. 用测试买家给当前已打开的客户发送一条文字，确认即使当前行有红点也会进入任务。
8. 再切到另一个客户，让测试买家发送一条消息，确认分组栏不会生成“会话 ID 缺失”循环，真实客户会进入任务表。
9. 检查完整链路：发现红点 → 打开客户 → OCR → V2 → Codex → 输入 → 发送。
10. 若失败，立即停止自动客服并保存实时进度窗口截图、应用日志和当时的 AX 诊断包；不要删除历史数据。

## 回滚

本候选版没有修改旧 App 或同事 B 原始 ZIP。出现问题时：

1. 停止并退出候选版；
2. 将备份的同事 B App 放回 `/Applications`；
3. 不删除 `Application Support` 中的聊天历史和任务记录；
4. 重新确认系统权限后启动旧版。
