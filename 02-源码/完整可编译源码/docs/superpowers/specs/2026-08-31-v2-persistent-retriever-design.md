# V2 常驻检索器与无完整 ZIP 回退设计

## 目标

把现有 V2 Top-12 检索从“每个客户问题启动一次 Python 并重建索引”改为“App 启动后只初始化一次，后续问题只查询”。必须保持现有知识库、章节切分、模型、融合权重、Top-12 规则、置顶文档、媒体规则和 36,000 字符上限不变。

成功标准：

- 同一 App 运行周期内，知识库 ZIP 最多打开和计算哈希一次。
- 同一 App 运行周期内，FastEmbed/ONNX 模型只创建一次，章节向量只加载一次。
- V2 失败时不把完整 ZIP 路径交给 Codex。
- 单个客户任务有限重试；检索服务在后台持续恢复，不永久卡住其他客户。
- 新旧检索器对封存问题返回相同的文档顺序和上下文内容。
- M1 冷启动不再受每次查询 5 秒硬时限影响；检索器就绪后的查询目标为 1 秒内完成。

## 当前问题

当前 `V2KnowledgeRetriever` 每次调用都会创建临时请求文件并运行一个新的 Python 子进程。Python 随后重新读取 228 MB ZIP、计算 SHA-256、解析全部 Markdown、建立内存 FTS、创建向量模型并加载 `.npy`。Swift `actor` 只串行化调用，并未保留 Python 进程。

检索超过 5 秒后，生产配置使用 `fallbackToFullInput`。Prompt 因此把 ZIP 路径交给 Codex，导致 Codex 再次执行 `unzip`、`rg` 或 `grep`，增加 token、延迟和硬超时风险。这也违反现有可靠性设计中“V2 检索失败时不得静默退回完整 ZIP”的要求。

当前知识库安装还有版本缺口：`Application Support/KnowledgeBase/current.zip` 只在文件不存在时复制。App 更新携带了新知识库时，旧 `current.zip` 不会自动更新。

## 方案比较

### 方案 A：仅放宽超时并预热一次

把 5 秒改成 20 秒，在启动时额外跑一次查询。实现最小，但每个客户问题仍重新启动 Python、读取 ZIP 和加载模型，不能消除根因。

### 方案 B：常驻 Python worker 与版本化持久索引

App 管理唯一一个 Python worker。worker 在启动时加载版本化索引、FTS、模型和向量，之后通过 JSONL stdin/stdout 接收查询。首次遇到新知识库版本时在临时目录建立索引，完成后原子切换。此方案保留现有 Python 排序算法，风险和工作量平衡最好。

### 方案 C：全部改写成 Swift

消除 Python 运行时，但必须重新实现中文分词、FTS、FastEmbed/ONNX 和排序，最容易破坏已验证的检索结果。本次不采用。

本设计采用方案 B。

## 组件与职责

### `RetrieverEngine`

Python 内存对象，生命周期与 worker 相同：

- 加载一个确定的知识库版本。
- 持有只读 `KnowledgeIndex`、`SemanticDocumentIndex` 和文档章节。
- 每次 `query(history_jsonl)` 仅执行现有查询提取、关键词排名、向量查询、融合和上下文压缩。
- 不保存任何客户查询状态；客户 A 的查询不能影响客户 B。

现有 `retrieve(request)` 保留为测试和兼容入口，但内部创建 `RetrieverEngine` 后调用一次查询。排序相关常量和函数不得修改。

### `serve_top12.py`

长驻 worker 入口：

- 启动参数只包含知识库、缓存和索引目录。
- 初始化完成后向 stdout 输出一条 `ready` JSON。
- stdin 每行接收一个带唯一请求 ID 的查询；stdout 返回同一 ID 的成功或错误 JSON。
- stdout 只允许协议 JSON；诊断信息写 stderr。
- EOF 或 `shutdown` 后正常退出。
- 单个请求异常只返回该请求错误，不终止 worker；无法继续使用的模型/索引错误才退出，由 Swift 监督器重启。

### 持久索引目录

目录为：

`Application Support/QianniuAutoReply/V2Indexes/<knowledge_sha256>/`

内容：

- `manifest.json`：知识库 SHA-256、算法版本、文档数、章节数、向量模型名。
- `sections.jsonl`：完整、顺序稳定的章节字段。
- `lexical.sqlite`：FTS5 表和章节定位信息。
- 语义向量继续使用现有按内容哈希命名的 `.npy` 和 `.json`。
- `ready.marker`：全部文件写入并校验后最后创建。

索引不存在或算法版本不一致时，在同级临时目录重建。只有完成自检后才原子改名到正式目录。进程崩溃留下的临时目录不得被当作有效索引。

### `V2KnowledgeRetriever`

Swift `actor` 从“每次调用一次 `BoundedProcess.run`”改为 worker 生命周期监督器：

- `prepare()` 启动 worker，等待 `ready`。
- `retrieve()` 复用已启动的 worker，通过管道发送一条查询并按 ID 等待回复。
- 启动准备和查询使用不同超时：冷启动不再使用 5 秒查询硬时限；就绪后的单次查询使用短超时。
- worker 意外退出时，当前查询最多自动重试一次。
- 管道读取、进程终止和继续读取必须由一个拥有者管理，避免多个 Task 同时消费 stdout。
- App 停止自动回复时可以保留已就绪 worker；App 退出时终止 worker。

第一版仍串行执行 V2 查询，以保证 ONNX 和排序行为与当前版本一致。因为热查询很短，串行不会成为明显瓶颈；不得在本次同时引入多线程排序变化。

## 启动与状态

用户点击“开始”后：

1. 保存运行意图。
2. 启动 V2 worker 准备任务。
3. UI 显示“知识库检索启动中”。
4. worker 就绪后显示“知识库检索已就绪”。
5. scheduler 可以继续发现和冻结客户消息，但生成阶段必须等待同一个准备任务，不能另起 worker。

如果冷启动失败，监督器在后台按 1、2、5、10、30、60 秒封顶持续重试。等待恢复不能持有千牛 UI lease，也不能阻挡其他客户的发现、OCR 或发送确认。

## 失败与降级

失败顺序固定为：

1. 常驻混合检索正常查询。
2. 单次查询失败且 worker 已退出：重启 worker一次并重试该客户一次。
3. 语义模型不可用但持久关键词索引有效：worker 返回 `v2-lexical-only` 的有界上下文。
4. worker 和关键词索引均不可用：该客户生成任务失败并进入现有任务隔离/稍后重试流程。

任何分支都不得把 `knowledgeBasePaths` 交给 Codex。`PromptBuilder` 在生产生成路径中必须要求非空检索上下文；没有上下文时抛出明确检索错误。

“有限/无限”边界：单个客户批次最多因 worker 重启重试一次；全局服务监督器可以无限后台恢复。这样不会无限重复同一客户，也不会因一次故障永久停止整个服务。

## 知识库版本更新

构建阶段为随包知识库生成一个小型 manifest，至少包含 SHA-256 和算法版本。

App 启动时读取随包 manifest：

- 本地版本相同：直接使用已有 `current.zip` 和索引，不重新读取完整 ZIP 验证。
- 本地版本不同：把随包 ZIP 复制到临时文件，校验随包声明的 SHA-256 后原子替换 `current.zip`，再后台建立新索引。
- 新索引建立完成前可以继续使用旧版本索引完成已冻结任务；新冻结任务切换到新版本后，Codex 客户会话版本随之失效并重新建立。

本地 manifest、ZIP 和索引版本必须一致；禁止混用旧章节与新向量。

## 回复能力不变约束

以下内容必须逐项保持：

- `BAAI/bge-small-zh-v1.5`。
- 章节切分和章节顺序。
- 关键词 token、BM25 后处理和模型路由。
- 文档融合 `constant=3`、权重 `(0.25, 1.0, 0.5)`。
- 章节融合 `constant=10`、权重 `(0.5, 1.0)`。
- 置顶政策文档、媒体文档规则、Top-12 和每文档章节上限。
- 最大上下文 36,000 字符。
- Prompt、模型和推理强度。

持久化改变的是加载时机，不改变查询输入或排序算法。

## 测试与验收

### Python

- worker 启动只构建一次 engine，连续两次查询不重新打开 ZIP。
- 持久索引第一次构建、第二次加载、损坏重建、算法版本变化重建。
- JSONL 请求 ID 一一对应，单次坏请求不杀 worker。
- 语义失败时返回有界的关键词结果，不出现 ZIP 路径。
- 对现有封存 V2 问题做新旧文档列表和上下文 SHA-256 对比。

### Swift

- 连续两次 `retrieve()` 只启动一个假 worker。
- worker 崩溃后只重启一次，单个客户不会无限重试。
- 启动和查询超时分离，错误文本反映实际超时而非硬编码“5 秒”。
- 并发调用不会串线请求 ID。
- 生产失败策略不允许 `fallbackToFullInput`。
- 无检索上下文时生成器不会把 ZIP 路径放入 Prompt。
- App 状态能区分启动中、已就绪、关键词降级和后台恢复。

### 性能和现场验收

- 当前 Mac 和 M1 各记录冷启动、连续 100 次热查询的 P50/P95。
- 100 次热查询期间 ZIP 打开次数为 0，Python 进程新增次数为 0。
- CLI 轨迹中不再出现针对配置知识库的 `unzip`、`zipinfo`、`rg` 或 `grep`。
- 以测试小号完成一条真实消息的捕获、检索、生成、Enter 发送和送达确认。

## 非目标

- 不修改 OCR、客户身份判断、页面置前、发送 Enter 行为或任务 FIFO。
- 不改变 gpt-5.6-sol、medium 推理或客服 Prompt。
- 不在本次把 Python 检索器改写成 Swift。
- 不在本次增加多个并发 ONNX 查询。
- 不删除现有日志、客户记录、知识库或旧索引；清理策略另行设计。
