# 千牛全自动客服通用自适应安装与自动配置设计

日期：2026-09-01  
状态：主体设计已批准；同事 B 真机失败补充规格待书面复核
代码基线：同事 B 可运行基线 `e1b0ab1bd2b35fa8aa00a9a3696fda00d7a441b3`，以及其上的会话行分类修复 `68509f83e688f3f632b7b58cc476d6cf34d9bbea`；本次补充规格基于通用媒体诊断提交 `a1a01a74cc1a7aced4990835f4aa91de4561b45b`

## 1. 背景与目标

当前程序在开发电脑和同事 B 的电脑上已经证明核心链路可以运行，但不同电脑上的 macOS、千牛版本、AX 树、屏幕缩放和窗口布局会产生结构差异。把某台电脑上的绝对坐标、固定 AX 层级或固定阈值直接复制到另一台电脑，会出现空白分组栏被当成客户、窗口匹配失败、输入框或发送控件选择错误等问题。

本项目的目标不是为同事 A、B、C、D 分别维护四份代码，而是交付同一个 Mac 安装包。软件第一次运行时自动探测本机能力、生成本机兼容配置、完成 OCR/V2/Codex 预热和只读自检；后续启动快速验证配置，页面结构发生变化时仅重新校准受影响的能力。

最终用户应只需要完成无法由 macOS 代替用户完成的动作：

1. 双击安装器；
2. 在系统设置中亲自开启辅助功能与屏幕录制；
3. 填写客服显示名；
4. 如果专用客服 Codex 尚未登录，先安全继承本机已验证的文件型登录缓存；无法继承时再完成一次设备登录；
5. 登录千牛并进入在线接待状态。

其余安装、资源校验、环境探测、配置生成、预热、自检和启动由程序完成。

## 2. 范围

### 2.1 本次包含

- Apple Silicon Mac（M1 及以后）的统一安装包；
- 单个 App 实例绑定一个千牛接待窗口；
- 首次运行向导；
- macOS 权限检测与设置页引导；
- 千牛窗口、客户列表、身份、聊天区、输入框、发送控件和截图坐标的自动校准；
- OCR、V2 常驻检索器和 Codex 运行环境的预热；
- 本机兼容配置的保存、验证、原子升级和回滚；
- AX、视觉和 OCR 的按能力混合降级；
- 脱敏诊断包和跨机器回归样本；
- 内部测试分发与正式签名、公证路径。

### 2.2 本次不包含

- Windows 千牛自动化；
- 一台 Mac 同时控制多个千牛商家账号；
- 自动填写千牛账号密码或绕过登录验证；
- 绕过 macOS 隐私授权；
- 云端遥控或远程自动更新兼容规则；
- 用机器学习模型取代可解释的 AX/视觉规则；
- 修改版本 A 冻结包。

多账号总控是独立架构问题，不能以删除“唯一窗口”检查的方式混入本次通用适配。

## 3. 设计原则

1. **同一份主程序，本机生成配置。** 机器差异进入配置和能力选择，不进入不同代码分支或不同 App 包。
2. **按能力自适应，不使用全局 AX/OCR 模式。** 窗口、客户身份、正文、输入和发送分别选择本机最可靠的实现。
3. **语义优先，相对几何次之，视觉兜底。** 不以绝对屏幕坐标作为唯一依据。
4. **一个失败不能拖死全队。** 单节点、单客户、单媒体或单服务失败只影响对应工作单元。
5. **旧配置在新配置验证完成前保持可回滚。** 禁止用未验证候选配置覆盖最后一个可用配置。
6. **就绪状态必须诚实。** “只读自检通过”和“真实发送已验证”是两个不同等级。
7. **配置不保存客户隐私。** 兼容配置只保存结构、比例、策略和摘要，不保存聊天、客户 UID、客户昵称或截图。
8. **客服 Codex 与个人 Codex 隔离。** 登录可以属于同一 ChatGPT 账号，但 Skills、规则、记忆和工作目录不能串入客服会话。

## 4. 总体架构

新增六个边界明确的组件，现有调度器只消费校准后的能力接口，不自行猜测本机结构。

### 4.1 `BootstrapInstaller`

负责安装包校验、安装位置选择、旧版本备份、原子替换和首次启动。它不参与千牛自动化。

安装优先放入 `/Applications`；当前用户无写入权限时放入 `~/Applications`。安装完成后才启动正式 App，禁止直接从 ZIP、微信目录、DMG 或 App Translocation 临时路径运行。

### 4.2 `FirstRunCoordinator`

驱动首次运行状态机，统一组织权限、千牛、客服名、Codex、校准、预热和自检。UI 只展示这个状态机的真实状态，不用多个模块各自推断“是否就绪”。

### 4.3 `EnvironmentProbe`

只读收集本机环境与能力：

- macOS 版本和 build；
- 芯片、进程架构；
- 千牛版本、build、PID、窗口 ID；
- 显示器、缩放、窗口坐标；
- AX 是否可读、节点和动作摘要；
- 屏幕截图与 AX 点坐标到像素坐标的映射；
- OCR、V2、Codex 可用性。

探测结果分成 `verified`、`fallback`、`unavailable`，不用一个总布尔值掩盖具体失败模块。

### 4.4 `CalibrationEngine`

把探测结果转换为可运行策略。每个定位器返回候选项、证据和能力等级，而不是直接返回一个坐标。只有通过交叉证据的候选项才能保存为主策略；证据不足时保存对应降级策略。

### 4.5 `RuntimeAdapter`

向现有调度器提供稳定接口，例如：

- `locateReceptionWindow()`
- `scanConversationRows()`
- `resolveCustomerIdentity()`
- `captureConversation()`
- `locateComposer()`
- `activateSend()`

内部根据本机配置执行 AX、相对几何或 OCR，不让调度器知道某台电脑的结构差异。

### 4.6 `CompatibilityProfileStore`

保存当前配置、候选配置和最后可用配置，负责版本迁移、校验、原子切换与回滚。配置文件损坏时不得删除最后可用配置。

## 5. 首次运行状态机

状态按以下顺序推进：

`installed → permissionsPending → qianniuPending → operatorPending → codexPending → probing → calibrating → prewarming → readOnlyReady → running`

另有三个非终止状态：

- `degraded`：部分能力使用降级路径，但仍可运行；
- `waitingExternalState`：等待用户授权、千牛登录或在线；
- `recalibrating`：运行环境改变，正在生成候选配置。

只有以下条件是真正硬前置：

- 没有辅助功能权限；
- 没有屏幕录制权限；
- 千牛没有可见接待窗口；
- 没有客服名；
- Codex 未登录且无法生成回复。

硬前置不满足时，App 保持打开并持续检测，不退出、不形成一秒一次的错误日志风暴，也不把状态描述为“运行中”。千牛暂时离线或窗口暂时不存在时进入等待状态，条件恢复后自动继续。

默认开启“全部就绪后自动运行”。用户完成最后一个人工步骤后不需要再寻找第二个启动按钮。

## 6. 安装与权限设计

### 6.1 分发形态

最终形态为 `千牛全自动客服-通用自适应版.dmg`，包含一个 `安装并启动.app`。安装器内部携带正式 App、知识库、OCR 资源、运行时、manifest 和哈希清单。

安装器执行：

1. 验证 manifest、SHA-256、签名、arm64 架构、磁盘空间；
2. 识别已有安装并创建可恢复备份；
3. 解压到同一磁盘的临时目录；
4. 校验临时目录；
5. 原子替换正式 App；
6. 写入不含凭证的安装收据；
7. 从固定安装路径启动。

任何校验失败都保留旧安装，不出现“旧版已删、新版又不能开”的中间状态。

### 6.2 Gatekeeper 边界

内部测试包在没有 Developer ID 和 Apple 公证时，第一次可能仍需右键“打开”。真正做到普通同事双击即开，必须使用 Developer ID Application/Installer 签名并提交 Apple 公证、staple 票据。安装器不能伪装成已经公证。

### 6.3 隐私权限

辅助功能和屏幕录制必须由用户在系统设置中明确开启。程序负责：

- 打开正确设置页；
- 显示当前待授权的正式 App，而不是旧版或临时路径；
- 每秒低成本轮询权限；
- 授权完成后自动进入下一步；
- 检测签名或安装路径变化导致的授权失效。

## 7. 自动校准算法

### 7.1 环境指纹

环境指纹由以下稳定字段组成：

- `macOSBuild`
- `hardwareArchitecture`
- `qianniuVersion` 与 `qianniuBuild`
- `qianniuRuntimeArchitecture`
- 当前显示器 scale 列表
- 接待窗口结构摘要
- 客户列表 AX 结构摘要
- 输入和发送区 AX 结构摘要

摘要由角色、动作、相对层级、空值分布和几何类别哈希组成，不包括真实文字内容。

### 7.2 接待窗口

候选窗口需属于选定千牛 PID，并综合：

- 标题含“接待”等语义；
- 可见、未最小化；
- 焦点状态；
- 最小合理尺寸；
- 左侧列表、中部聊天和底部输入区域的结构证据；
- AX 窗口与屏幕捕获窗口的几何相似度。

坐标误差使用显示器 scale 和实测映射计算，不再用所有电脑共享的单一像素阈值。多个候选同分时只延迟当前 UI 动作并重新探测，不杀死整个调度器。

### 7.3 客户行与分组栏

程序先采样多个同级节点，计算正常会话行的中位高度、宽度、间距、可点击动作和文字分布，再分类：

- **正常客户行**：存在客户身份候选，或存在红点且结构接近正常会话行；
- **分组栏/装饰节点**：无身份、无红点，且高度/动作/位置符合分组结构；
- **待确认行**：有红点但身份仍不可解析；
- **无关节点**：不进入任何客户任务。

任何单行异常只产生该行的诊断记录，禁止让 `scanConversationRows()` 整体抛弃已经确认的正常行。

分组栏判断使用相对高度。例如“比本机正常行显著矮”是证据，“固定 34 像素”不是规则。已有的 34 像素兼容逻辑保留为样本，不成为全局常数。

### 7.4 客户身份

每台电脑自动得到身份来源优先级：

1. 会话行容器的完整 AXTitle/UID；
2. 会话行子节点昵称；
3. 聊天顶部完整身份；
4. 已确认身份的唯一截断前缀；
5. OCR 昵称。

身份匹配保存来源和证据。截断前缀只在当前可见客户中唯一时使用；之后出现同前缀冲突时，相关任务转入待确认而不是继续沿用旧映射。

### 7.5 聊天、输入和发送

聊天区按窗口内相对布局和消息结构定位；OCR 裁剪区域保存为窗口比例，不保存屏幕绝对坐标。

输入框与发送控件分别探测 AXRole、AXAction、标题和相对位置。发送策略按控件真实能力选择：

- `AXButton` 且支持 `AXPress`：执行 `AXPress`；
- 复合菜单按钮需要 Return：输入框聚焦后使用 Return；
- 无可执行 AXAction：使用经本机校准的点击中心作为最后降级。

“找到了按钮”与“发送完成”是两个事件。第一次真实发送后，只有输入框清空或出现新客服气泡，才把本机状态升级为 `endToEndVerified`。

#### 7.5.1 同事 B 的 40 个可按按钮回归与发送候选评分

同事 B 的真实安装证明，`AXPress` 只能说明控件“可以按”，不能说明它是发送按钮。旧实现把所有 `role` 含 `Button` 且支持 `AXPress` 的节点都标记为 `send-control`，本机因此产生 40 个发送候选，无法生成唯一 `sendPolicy`；候选 profile 被拒绝，OCR/V2 甚至没有机会预热。

新分类必须将“控件类别”和“发送候选”分开：

- 标题精确等于“发送”的控件标记为强语义候选；
- 其他支持 `AXPress` 的按钮只标记为普通可按控件，不得直接成为发送按钮；
- 发送候选只能来自输入区附近，并使用相对位置、共同祖先、角色、动作和标题共同评分；
- 工具栏、刷新、设置、列表和聊天区上方的按钮必须排除；
- 最高分候选必须同时满足最低证据门槛并显著高于第二名，才保存为已验证按钮；
- 无唯一高置信候选时不拒绝整份 profile，而是保存 `.returnKeyOnce`，并把 `sendAX` 标记为 `fallback`；
- 只有输入框也无法定位、无法建立任何可执行发送路径时，才阻止进入 `readOnlyReady`。

选择结果必须记录：原始可按节点总数、进入发送评分的节点数、最终策略、证据等级、采用降级的原因。诊断记录不得包含客户文字。

这条规则保证以下真实输入可运行：

`40 个 AXPress 控件 → 1 个精确“发送”且位置正确 → 选择真实发送控件`

以及：

`40 个 AXPress 控件 → 无法唯一确认“发送” → 使用 Return 降级 → 继续预热与运行`

### 7.6 坐标系统

校准时用同一窗口的 AX frame 和 CGWindow frame 计算 points-to-pixels 映射，并按显示器分别保存。窗口移动到另一显示器、缩放改变或映射漂移时，只重新校准截图和点击坐标，不重建无关的 Codex/V2 配置。

## 8. 本机配置模型

配置分成三个文件：

1. `InstallationState.json`：安装路径、版本、资源哈希；
2. `OperatorConfig.json`：客服别名、自动启动偏好；
3. `MachineCompatibilityProfile.json`：结构和能力策略。

兼容配置的逻辑结构为：

```json
{
  "schemaVersion": 1,
  "profileID": "generated-uuid",
  "fingerprint": {
    "macOSBuild": "25G83",
    "qianniuBuild": "20260812105806",
    "architecture": "arm64",
    "displayScales": [2.0],
    "axStructureDigest": "sha256:fixture-digest"
  },
  "window": { "primaryStrategy": "focusedReception", "fallbacks": [] },
  "conversationList": {
    "rowModel": {},
    "identityOrder": ["containerTitle", "childName", "header", "prefix", "ocr"]
  },
  "capture": { "coordinateMapping": {}, "relativeRegions": {} },
  "composer": { "inputStrategy": {}, "sendStrategy": {} },
  "capabilities": {},
  "validation": { "readOnlyPassedAt": "2026-09-01T08:00:00Z", "endToEndPassedAt": null }
}
```

写入流程为 `candidate → fsync → schema/hash 校验 → read-only 验证 → 原子 rename`。旧配置保留为 `last-known-good`。配置 schema 升级失败时回滚，不静默丢弃。

### 8.1 通用版首次启动与旧候选版状态迁移

现有候选版和通用版暂时共用过运行记录目录。同事 B 已经出现旧 `OperatorConfig.json` 中 `autoStartWhenReady=false` 被新通用版继承，导致安装完成后仍保持停止。新版本必须增加独立的通用版安装标记和一次性迁移规则：

1. 首次发现通用版安装标记不存在时，保留旧聊天记录、图片指纹、客户身份映射和发送判重数据；
2. 不继承旧候选版的临时“停止”运行意图；
3. `autoStartWhenReady` 按通用版默认值 `true` 初始化；
4. 完成迁移后原子写入安装标记；
5. 用户以后在通用版 UI 中手动关闭自动启动时，必须尊重并持久保存，不得每次启动重新改为 `true`；
6. 迁移不得重放旧回复、丢失图片判重或清空客户历史。

首次向导达到 `readOnlyReady` 后，若迁移后的当前偏好仍为 `true`，已有 `FirstRunCoordinator → AutomationAppModel` 链路必须恰好启动调度器一次；反复状态通知不得造成重复启动。

## 9. Codex 自动配置与隔离

客服继续使用固定专用目录：

- `<runtime-root>/客服Codex/CODEX_HOME`
- `<runtime-root>/客服Codex/Workspace`

该目录不包含用户个人的 Skills、AGENTS.md、rules、plugins 或 memories。Codex 固定在空白 Workspace 运行，并继续使用现有模型与推理等级。

登录处理采用明确且可支持的流程：

1. 先执行专用 `CODEX_HOME` 的 `codex login status`；
2. 已登录则直接通过；
3. 未登录时，若本机默认 `~/.codex/auth.json` 是非空普通文件，先在默认 `CODEX_HOME` 中验证该登录确实有效；
4. 验证有效后只将 `auth.json` 原子复制到专用目录，权限固定为 `0600`，再在专用目录复核登录；
5. 不复制 `config.toml`、Skills、AGENTS、rules、plugins、memories、history 或 sessions；
6. 文件不存在、钥匙串存储、复制失败或复核失败时，由向导启动一次 `codex login --device-auth` 并等待完成；
7. 任何继承失败都只回退授权，不能阻塞其他本地就绪状态；
8. 绝不把任何同事的凭证打进安装包、日志或诊断包。

不使用个人 `auth.json` 的符号链接。使用本机验证后的原子副本，避免个人 Codex 退出登录或替换文件时破坏客服运行，同时保持登录以外的状态隔离。

每次客服调用继续禁止搜索文件、读取 Skill 和运行命令。发现工具调用时当前 session 标记为污染，下轮轮换；这与自动配置文件彼此独立。

## 10. 预热与就绪等级

预热顺序：

1. OCR 进程和模型；
2. V2 常驻检索 worker、ZIP/索引/向量；
3. Codex 登录检查和隔离目录检查；
4. 一次不会发送到千牛的最小生成探针。

UI 显示两个就绪等级：

- `可运行（只读自检通过，发送尚未验证）`；
- `全链路已验证（至少一次真实输入和发送后确认通过）`。

只读自检通过即可按照用户设置自动运行，不能因为没有专门测试客户而永久卡在安装向导。第一次真实发送会自动完成全链路验证。

## 11. 运行时再校准

每次启动做快速验证：

- 版本和环境指纹是否相同；
- 接待窗口是否仍可定位；
- 客户列表、输入和发送的关键结构是否仍存在；
- AX 与截图坐标是否仍对齐。

无变化时直接使用旧配置。以下事件触发局部再校准：

- macOS 或千牛 build 改变；
- 窗口结构摘要改变；
- 显示器或 scale 改变；
- 同一能力连续两次定位失败；
- 操作后的实际结果与预期不符。

再校准在候选配置中进行。能继续使用最后可用配置的模块照常工作；只有受影响的 UI 能力短暂降级或排队。新候选验证完成后原子切换。

## 12. 故障隔离

| 故障 | 动作 |
|---|---|
| 单个 AX 节点无 UID | 忽略/待确认该节点，继续返回其他正常客户 |
| 已知客户第一次找不到 | 当前任务放到队尾 |
| 第二次仍找不到 | 结束本次任务，保留客户历史与身份映射 |
| 图片复制失败 | 放弃本次媒体，不无限点击；不堵塞其他任务 |
| OCR 服务失效 | 后台重建；已经生成的发送任务继续执行 |
| V2 worker 失效 | 后台重启并使用本地关键词降级；禁止完整 ZIP 回退给 Codex |
| Codex 未登录 | 生成队列等待登录，扫描和本地任务状态继续维护 |
| Codex session 调用工具 | 标记污染，下轮换新 session |
| 当前接待窗口暂时消失 | 进入等待并低频重探测，不清空任务 |
| 配置候选验证失败 | 回滚最后可用配置并导出诊断证据 |
| 单个发送结果不确定 | 标记 uncertain、释放队列，不自动重复发送同一答案 |

除权限、没有任何接待窗口和没有生成能力等物理前置条件外，不设置能让一个客户错误把全局调度器永久停住的门禁。

## 13. 跨机器兼容验证

建立脱敏 fixture 库，至少包含：

- 当前开发电脑；
- 同事 A：M1 的 AX/窗口/红点样本；
- 同事 B：M2、macOS 15.7.3 和已确认可运行结构；
- 后续同事 C、D 的首次探测样本。

每份 fixture 包含：

- 环境指纹；
- 脱敏 AX 树；
- 窗口元数据；
- 红点和关键布局的脱敏局部图；
- 期望的客户行、分组栏、窗口、输入和发送策略；
- 配置生成结果。

每次发布必须离线回放所有 fixture，并满足：

1. 分组栏不创建客户任务；
2. 单个坏节点不阻断正常客户；
3. 完整 UID、昵称、截断前缀和 OCR 降级按预期选择；
4. 接待窗口不会被工作台替代；
5. 输入和发送策略与控件真实动作匹配；
6. points-to-pixels 映射在各缩放样本中正确；
7. 配置损坏或升级失败可回滚；
8. 不把客户内容写入兼容配置或诊断摘要。
9. 同事 B 的 40 个可按控件 fixture 不会产生 40 个发送控件；能唯一定位时选择真实发送按钮，不能唯一定位时生成 Return 降级策略；
10. 发送候选不唯一不会阻断 OCR/V2 预热或 `readOnlyReady`；
11. 首次从旧候选版迁移时默认自动启动一次，但保留聊天、图片指纹和客户身份数据；
12. 用户在通用版内手动关闭自动启动后，后续重启不会重新开启。

真机验收分两层：

- 每台新电脑先通过只读安装、权限、校准和预热；
- 使用测试客户完成一次文字消息全链路，再按需要测试图片和连续消息。

## 14. 诊断包

未知电脑无法校准时，一键生成脱敏诊断包，包含：

- 软件和环境版本；
- 各能力状态及失败阶段；
- 脱敏 AX 结构；
- 窗口与坐标映射；
- 配置候选与最后可用配置的结构差异；
- OCR/V2/Codex 预热耗时；
- 最近有限条结构化错误；
- 重现和验收命令。

默认不包含登录凭证、完整聊天、客户 UID/昵称、原始全屏截图和个人 Codex 配置。需要原始证据时必须由用户明确勾选。

校准错误必须使用可执行的中文结构化诊断，至少包含：

- 失败阶段，例如“发送控件校准”；
- 原始候选数与有效候选数，例如“40 / 1”；
- 最终选择或降级策略；
- 是否仍允许继续预热和运行；
- 用户或接管 Codex 的下一步动作。

可恢复校准问题由状态机低频重试，不能每秒产生一整屏相同错误。发送按钮不唯一属于可降级问题，不得显示为整机 `degraded`；只有不存在任何发送路径时才进入阻塞状态。

### 14.1 可移植的 Codex 完整接管包

同事电脑上的 Codex 必须能够在不依赖开发电脑路径的情况下复现、修改、测试和重新安装项目。交付包同时包含：

1. 当前提交的无 `.git` 源码快照，供直接阅读；
2. 使用 `git bundle create 千牛全自动客服-完整历史.bundle --all` 生成的完整 Git 历史 bundle；
3. 发布提交号、分支、文件清单和 SHA-256；
4. 构建、测试、签名、安装、校准、预热和诊断命令；
5. 单一入口文件“把这个文件交给 Codex-项目完整接管与Debug手册.md”；
6. 不含客户运行数据、聊天、图片指纹、登录凭证、个人 `~/.codex`、构建缓存和绝对工作树指针。

不能直接复制 linked worktree 内的 `.git` 文件，因为它通常只是指向开发电脑绝对路径的文本指针，在同事电脑必然失效。也不能只使用 `git archive` 后声称“包含完整 Git”；`git archive` 只适合源码快照。接管 Codex 应先执行 `git bundle verify`，再从 bundle 克隆出真正可修改的工作区，并校验 HEAD 与发布提交一致。

接管手册必须允许 Codex 自动完成：安装包校验、备份旧版、权限状态检查、只读 AX 探测、fixture 生成、TDD 修复、全量测试、重新构建安装、OCR/V2/Codex 预热和就绪确认。它不得声称能绕过 macOS 辅助功能/屏幕录制授权、替用户登录千牛或自动取得 Developer ID 公证。

## 15. UI 要求

首次向导只显示用户能理解的阶段：

1. 安装完成；
2. 开启权限；
3. 登录并打开千牛；
4. 填写客服名字；
5. 登录客服 Codex；
6. 正在认识这台电脑；
7. 正在预热；
8. 可运行/全链路已验证。

高级区域展示每个能力的策略和状态，例如“客户身份：AX 完整标题”“消息正文：OCR”“发送：Return”。不能只显示一个笼统的绿色“正常”。

运行浮窗继续显示真实阶段，但校准日志与客户任务日志分开，避免环境重试淹没客户处理过程。

## 16. 实施边界和阶段

为降低一次性变更风险，实现分三阶段，但三阶段共用本设计的数据模型和接口：

### 阶段一：安装、状态机与配置基础

- 安装器；
- 首次向导；
- 权限、千牛、客服名、Codex 登录检查；
- 配置 schema、原子存储、回滚；
- OCR/V2/Codex 预热状态。

### 阶段二：自动校准与 RuntimeAdapter

- 环境指纹；
- 窗口、客户行、身份、聊天、输入、发送和坐标校准；
- 现有模块改为消费统一 RuntimeAdapter；
- 局部降级和局部再校准。

### 阶段三：跨机器验收与正式分发

- A/B/当前电脑 fixture；
- 真机只读和全链路测试；
- 诊断包；
- DMG、签名、公证和安装回滚验证。

每个阶段完成后都必须保持现有同事 B 基线可回滚。版本 A 始终只读冻结。

## 17. 验收标准

在同一安装包下，当前电脑、同事 A 和同事 B 分别满足：

1. 用户不需要修改源码或运行终端命令；
2. 授权、千牛、客服名和 Codex 登录之外的配置自动完成；
3. OCR 与 V2 在开始运行前完成预热；
4. 不因空白 AXGroup 或分组栏阻断客户列表；
5. 接待窗口、客户身份、聊天区、输入和发送均显示实际选择策略；
6. 重启后复用配置，快速验证通过时不重复完整校准；
7. 改变窗口尺寸、移动显示器或升级结构样本后能局部再校准或回滚；
8. 单任务失败不会停止其他客户或全局扫描；
9. V2 失败不会把完整 ZIP 交给 Codex；
10. 客服 Codex 不加载个人旧 Skill；
11. 兼容配置和默认诊断包不含客户隐私或登录凭证；
12. 首次真实测试消息能够完成发现、阅读、V2、Codex、输入、发送和发送后确认。
13. 同事 B 的 40 个可按按钮样本能够生成非空 `sendPolicy`，且不会在发送校准阶段阻止 OCR/V2 预热；
14. 第一次安装通用版时默认在全部就绪后自动开始，后续尊重用户主动关闭的偏好；
15. 交付包的 Git bundle 可在一个临时目录通过 `git bundle verify` 并克隆，克隆后的 HEAD 等于发布提交；
16. 接管包中的源码、Git bundle、DMG 和手册哈希全部可复核，且扫描不到客户数据或登录凭证。

## 18. 关键风险与控制

- **错误校准被保存。** 使用交叉证据、候选配置、只读验证和最后可用配置回滚。
- **千牛运行中结构改变。** 对能力做局部摘要和再校准，不全量清空状态。
- **外接显示器导致坐标漂移。** 按窗口和显示器维护 points-to-pixels 映射。
- **专用 Codex 未登录。** 首次向导先尝试继承本机有效文件型登录缓存，失败再处理设备登录，不把它误报成模型超时。
- **复制个人 Codex 配置重新引入旧 Skill。** 只复制验证后的 `auth.json`，不复制个人 CODEX_HOME 的其他内容。
- **未公证安装包让同事误以为损坏。** 内测说明真实披露 Gatekeeper 步骤；正式发布前完成 Developer ID 和公证。
- **自动配置被误解为兼容所有未来页面。** 对已知 fixture 给出确定性回归；未知结构自动探测、降级并产生诊断包，不声称无条件兼容。
- **把所有可按按钮都当成发送。** 普通 `AXPress` 只进入通用控件集合；发送必须经过输入区邻近、语义和结构评分，歧义时使用 Return 降级。
- **降级发送误发换行。** 首次真实发送仍使用输入框清空/新客服气泡做结果确认；不确定则标记 `uncertain` 并释放任务，不自动重发。
- **旧候选版的停止偏好让新安装永远不启动。** 首次通用版迁移只保留业务历史与判重，不继承临时停止意图；写入迁移标记后再尊重用户的新偏好。
- **复制 `.git` 后在同事电脑失效。** 交付完整 `git bundle`，并在打包验收中真实 verify、clone 和比对提交。

## 19. 决策记录

- 采用“首次运行自动校准”的方案 2；
- 不采用每台电脑人工维护独立参数包；
- 不采用全局纯 OCR 方案；
- 不采用把个人 `~/.codex` 整体复制给客服程序；
- 不在首版自动复用个人 auth 符号链接，先使用专用设备登录；
- 不把多千牛账号总控纳入本次范围；
- 不修改版本 A，以同事 B 可运行版本为新开发基线并始终保留回滚能力。
- 不把 `AXPress` 等同于发送按钮；发送控件必须进行区域与结构评分；
- 发送按钮歧义时采用 `.returnKeyOnce` 降级，继续完成预热和运行；
- 通用版第一次迁移默认自动运行，同时保留旧聊天和判重数据；
- 接管包同时提供源码快照和完整 Git bundle，不再把 `git archive` 描述为完整开发仓库。
