# 客户已回复游标与冻结批次设计

日期：2026-08-28

## 背景

当前系统同时依赖客户消息修订值、单个待处理指针和“当前可见聊天的最后发言者”。当任务 A 已冻结并生成，而客户随后发送 B、C 时，A 的客服回复可能在历史记录中排在 B、C 后面。系统因此把 B、C 错判为已被该客服消息覆盖，直到客户再次发送 D、出现新红点后才重新提交 B、C、D。

这个问题不是 OCR 漏读：B、C 已经写入 `history.jsonl`。根因是系统没有持久记录“哪一批客户事件已经由自动回复确认发送”，而试图从客服消息的相对位置推断回答关系。

## 目标

- 对每位客户持久记录自动回复已经确认覆盖到的客户事件位置。
- 每个生成任务冻结一个不可变的客户消息区间；后来的客户消息不得替换、取消或改写已经就绪的回复。
- A 发送成功后，系统必须主动提交已经观察到的 B、C，不依赖新的红点。
- 同一冻结批次内连续到达的文字、图片和链接可合并为一条回答。
- 任务、应用或 CLI 重启后仍可准确恢复未发送批次和已回复位置。
- 保持现有 OCR 解析、媒体复制、知识库、模型、发送器和每客户 Codex 会话机制不变。

## 非目标

- 不重写 OCR 识别或聊天去重算法。
- 不改变发送按钮定位、回读确认或千牛置前逻辑。
- 不为人工客服建立协同工作流。本阶段中，只有本程序确认发送成功才推进游标；普通客服消息仍作为上下文，但不自动声明客户批次已完成。
- 不改变模型或推理强度。

## 核心不变量

1. 每个客户事件具有稳定、有序的身份。
2. 每个任务覆盖 `(startCursor, endCursor]` 区间。
3. 同一客户的未完成任务区间不得重叠或倒退。
4. 只有发送结果为 `sent` 的任务才能把已回复游标推进到自己的 `endCursor`。
5. 客服消息、OCR 可见顺序和红点状态都不能推进已回复游标。
6. 一旦任务冻结，新增客户消息只能进入后续批次。
7. 已回复游标必须是当前客户事件序列的合法前缀；否则停止推进该客户的游标并保留持久证据，不能静默跳过消息。

## 客户事件身份与游标

沿用现有客户事件规范化逻辑：

- 文字和链接使用采集身份、批次内序号、类型、时间和内容。
- 图片使用图片文件内容哈希，不使用易变文件名。
- `read_status`、`created_at` 和客服消息不参与客户事件身份。
- 同一采集批次内的重复内容保留各自序号；不同采集批次的相同内容不会因文本相同而自动合并。

游标由两个字段组成：

- `count`：规范化客户事件前缀的事件数量。
- `digest`：该前缀的链式 SHA-256 摘要。

同时保存数量和摘要，既能快速切分批次，又能验证历史仍然是原先的追加前缀。空游标表示尚未回复任何客户事件。

## 持久状态

调度器状态升级一个 schema 版本，新增：

- `answeredCursors[uid]`：每个 UID 最近一次确认发送成功的游标。
- 每个 `SchedulerRecord` 的 `startCursor`、`endCursor`。
- 每个冻结快照的 `targetHistoryJSONL`：本任务区间内的客户消息，保留其文字、图片和链接次序。

迁移规则：

- 旧的非终态任务从其冻结快照计算 `endCursor`。
- 从现有已确认发送记录及归档中的客户修订值，选择能匹配当前历史的最新合法前缀作为已回复游标。
- 某 UID 没有活动任务、没有待处理指针且没有可恢复发送记录时，把迁移时的当前客户事件尾部设为基线游标，避免把导入的旧聊天重新回复一遍。
- 某 UID 存在活动任务或待处理指针，但无法证明其起始前缀时，隔离该 UID 并保留全部文件和诊断证据；不得猜测游标、删除指针或影响其他 UID 运行。

状态写入继续使用现有原子保存和归档机制。

## 捕获与批次形成

一次捕获完成后：

1. 从 `history.jsonl` 计算完整、有序的客户事件序列和当前游标。
2. 读取该 UID 的 `answeredCursor`。
3. 验证 `answeredCursor` 是当前序列的前缀。
4. 排除已经被该 UID 的冻结或未完成任务覆盖的区间。
5. 若仍有未覆盖客户事件，把连续尾部冻结为新任务。

是否形成任务不再依赖 `latestSpeaker == customer`。OCR 导出器只要确认出现新的客户内容，就更新该 UID 的待处理指针；可见客服消息不能取消这个事实。

待处理指针继续承担“本地历史已经可靠落盘”的交接职责。任务成功发送后，只删除与该任务 `endCursor` 精确匹配的旧指针；更新过的较新指针必须保留。

## 生成与发送时序

假设当前已回复游标为 0：

1. A 到达，冻结任务 `(0, A]` 并开始生成。
2. B、C 到达，写入历史并标记该 UID 存在更新，但不改变任务 A。
3. A 回复就绪后优先发送 A。
4. 只有 A 的发送结果为 `sent`，才原子地把游标推进到 A。
5. 调度器立即为该 UID 安排一次新捕获；捕获把 `(A, C]` 冻结为 B+C 任务。
6. B+C 生成期间 D 到达时，B+C 仍先发送；成功后游标推进到 C，再形成 `(C, D]`。

红点仅用于发现尚未进入调度器的客户。只要某个 UID 已经被观察到有后续客户修订，后续批次由持久状态驱动，不需要等待红点重新出现。

## Prompt 数据契约

模型仍收到完整聊天记录作为上下文，同时新增明确的冻结目标区：

- `full_history.jsonl`：完整会话上下文。
- `target_customer_batch.jsonl`：严格对应 `(startCursor, endCursor]` 的客户事件。
- 当前批次图片附件，仅包含目标区间的图片。

Prompt 明确要求：只回答 `target_customer_batch.jsonl` 中的问题；一条回复覆盖该批次内所有尚需回答的事项；后续未进入该目标区间的消息不得改变本轮回复。

每客户 Codex 会话仍可复用，但会话记忆不能代替本地游标。本地游标和已确认送达记录始终是真实状态来源。

## 客服消息语义

本阶段不再用客服消息的位置推断客户批次是否完成：

- 程序自己的 A 回复即使显示在 B、C 后面，也只完成 A 的任务区间。
- 普通客服消息保留在完整上下文中供模型理解。
- 只有调度器获得发送器的 `sent` 结果后，才推进对应任务的游标。

如果以后需要“人工回复后取消 AI”，应新增明确的人工接管信号或可靠的出站归属记录，不能重新采用“最后发言者”推断。

## 故障与恢复

- 生成失败：保留相同冻结区间重试，不扩大到后续客户消息。
- 发送前失败：保留已经生成的回复和区间，优先重试发送。
- 发送结果不确定：不推进游标，维持现有不确定状态和证据。
- 确认发送成功：在同一次持久提交中完成任务并推进游标，然后安排后续捕获。
- 应用重启：恢复非终态任务；按游标重新计算尚未覆盖的客户尾部。
- 历史不再匹配游标前缀：隔离该 UID 的游标推进并记录具体校验错误，其他客户继续运行。

## 测试策略

### 单元测试

- A 生成期间到达 B、C；A 成功后形成 B+C。
- A 发送动作期间到达 B、C。
- B+C 生成期间到达 D。
- A 的客服回复在历史中位于 B、C 后面。
- 同一批次中的多个问题合并为一个目标批次。
- 连续相同文字具有不同事件身份。
- 图片、链接、图片加文字均进入正确区间，并只附带本批次图片。
- 旧红点消失后，已观察到的后续批次仍自动运行。
- 重复 OCR 不产生重复任务。
- 旧待处理指针不能覆盖较新的指针。

### 恢复测试

- 在捕获、生成、回复就绪、发送前、发送后状态保存之间分别模拟退出。
- 验证只有确认发送成功的批次推进游标。
- 验证重启不会漏答或重复提交已经完成的区间。

### 集成测试

- 使用假驱动穷举 A/B/C/D 在各 await 边界到达的交错顺序。
- 验证同一 UID 严格按批次发送，不同 UID 仍可并发生成。
- 验证发送优先于新的 UI 捕获操作。

### 真实链路验证

在测试小号上依次验证：

1. A 后快速发送 B、C。
2. 等 A 开始生成后再发送 B、C。
3. A 即将发送时发送 B、C。
4. B+C 生成时发送 D。
5. 重复上述流程，并包含图片和链接。

验收标准是每个客户事件恰好进入一个冻结批次，批次按顺序确认发送，且任何后续批次都不依赖额外红点才能启动。
