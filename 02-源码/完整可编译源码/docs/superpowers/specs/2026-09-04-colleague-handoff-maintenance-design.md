# 版本 B 同事交付、首次配置与自动维护设计

## 目标

生成一个可通过微信发送的完整 ZIP。非技术同事只需解压并把整个文件夹交给其 Mac 上的 Codex；Codex 随后完成安装、权限引导、千牛文本模式确认、客服名称配置、本机自适应校准、预热、自检、启动教学与长期磁盘维护。

本次不改变版本 B 的红点、AX、OCR、图片、视频、知识检索、Codex 回复、发送或转人工业务算法。

## 交付包结构

```text
千牛全自动客服-版本B-完整交付包-<时间>/
├── 00-先看这里/
│   └── 把这个文件交给Codex-安装配置维护与Debug手册.md
├── 01-安装/
│   ├── 千牛全自动客服-版本B.dmg
│   └── 首次安装说明.txt
├── 02-源码/
│   ├── 完整可编译源码/
│   ├── 源码快照.zip
│   └── 工程师构建与Debug说明.md
├── 03-Git完整历史/
│   └── 千牛全自动客服.bundle
├── 04-自动维护/
│   ├── 安装自动清理.command
│   ├── 检查并安全清理.command
│   └── 自动清理规则.md
├── 05-故障处理/
│   └── 一键导出诊断包.command
└── 06-校验/
    ├── manifest.json
    └── SHA256SUMS.txt
```

ZIP 不包含开发电脑的客户聊天、视频、图片、任务状态、Codex 凭证、Cookie、Token 或其他运行数据。

源码不是只读参考：同事的工程师和 Codex 必须能在新电脑上直接修改、测试、构建并重新安装。源码区应包含当前版本 B 的全部 Swift、Python、资源、测试、构建脚本、安装脚本和文档；Git bundle 应包含可恢复的完整提交历史。工程师说明必须写明工具链版本、依赖位置、离线资源、常用测试命令、App/DMG 构建命令、签名与权限注意事项，以及从 Git bundle 恢复仓库的方法。不得把 `.build`、临时缓存或本机运行数据伪装成源码依赖。

## Codex 首次接管流程

手册第一部分必须直接面向接手电脑上的 Codex，并要求它顺序执行：

1. 校验 `SHA256SUMS.txt`、DMG、Git bundle 和源码提交一致性。
2. 将 App 安装到固定路径 `/Applications/千牛全自动客服-版本B.app`，不得从微信目录、ZIP 内部、Downloads 随机目录或 App Translocation 路径长期运行。
3. 第一次打开若被 Gatekeeper 阻止，逐步引导用户使用右键“打开”，或进入“系统设置 → 隐私与安全性 → 仍要打开/Open Anyway”。不得尝试绕过系统安全机制。
4. 引导用户为正式安装路径下的 App 开启“辅助功能”“屏幕与系统音频录制”和需要的语音识别权限。授权后退出并重新打开正式 App，避免权限授给旧路径或临时副本。
5. 引导用户在千牛中进入：
   `设置 → 系统设置 → 接待设置 → 会话窗口 → 文本模式`。
   必须明确说明气泡模式不受支持；Codex 应让用户确认界面已经选中“文本模式”，不能只假设完成。
6. 让用户在 App 首次配置页填写自己的客服名称/ID。不得沿用开发电脑的“小丹”“小甘”等值。
7. 确认千牛已登录、在线并打开正确的“接待中心”；不得把千牛工作台主页当成接待中心。
8. 运行 App 自带的本机自适应校准，只读采集当前 macOS、千牛版本、窗口、缩放与 AX 结构，生成本机配置。
9. 预热 OCR、V2 常驻检索器、视频语音识别与 Codex 登录检查。
10. 在不发送消息的自检通过后，向用户说明即将进入正常运行；启动并观察至少一个扫描周期。
11. 用普通中文教会用户开始、停止、查看队列、识别错误、查看视频进度和导出诊断包。
12. 告知工程师源码和 Git 历史的位置，并实际执行一次源码测试或只构建验证，证明交付内容可以继续开发，而不只是能安装现成 App。

任何一步失败时，Codex 必须停在该步给出具体按钮和路径，不得宣称“全部 setup 完成”。

## 本机路径与自适应

所有运行目录必须通过当前登录用户的 `Application Support` 动态确定，禁止写死 `/Users/scy` 或其他开发电脑用户名。首次使用相关功能时，由程序创建缺失目录。

典型根目录：

```text
~/Library/Application Support/
QianniuAutoReplyTaskIsolationCandidate/
AI客服记录-任务隔离候选版/
```

同事电脑上的用户名、磁盘卷名和绝对路径可以不同。提交给 Codex 的图片帧必须来自该机运行时生成的绝对路径。

## 自动维护机制

### 稳定安装位置

安装脚本将维护工具复制到：

```text
~/Library/Application Support/
QianniuAutoReplyTaskIsolationCandidate/Maintenance/
```

定期任务只调用这里的稳定副本，不能依赖用户一直保留微信 ZIP 解压目录。

### 触发条件

Codex 在首次 setup 时创建一个附着于当前安装任务的每日自动检查：

- 每天运行一次轻量检查；
- 距上次实际清理达到 30 天时清理；
- 运行数据达到或超过 10 GiB 时立即清理；
- 超限清理目标为降到 8 GiB以内，给后续数据留下缓冲。

如果当前 Codex 环境无法建立自动任务，必须明确告诉用户，并提供“双击检查并安全清理.command”的人工替代方式。

### 可删除范围

清理器只处理白名单中的数据：

1. `video-analysis-inbox.json` 中 phase 明确为 `completed` 的视频；
2. 上述视频 `messageHash` 对应的原始 `.mp4`；
3. 对应的抽帧、音轨和 manifest 目录；
4. 对应的旧兼容视频证据目录；
5. 过期的非活动 CLI 调试轨迹和可再生成的临时文件。

正常的 30 天清理只删除完成时间超过 30 天的白名单文件。达到 10 GiB 时，可继续从最旧的 `completed` 视频开始清理，直到降至 8 GiB；不得删除未完成数据来强行满足容量目标。

清理后保留视频状态中的紧凑完成记录和内容哈希，防止旧消息被重新当成新视频。不得留下会重新进入待处理队列的状态。

每个进入 `completed` 的视频必须记录明确的完成时间；30 天保留期从该时间开始计算。旧状态若没有完成时间，清理器不得依据文件修改时间猜测并删除，只能保留并在维护日志中标记为“缺少完成时间”。

### 永不删除范围

- 正在等待地址、下载、抽帧、转写、生成、发送或确认的任务；
- phase 为 `downloaded`、`preparingEvidence`、`readyForGeneration`、`admitted` 或 `failed` 的视频；
- 客户聊天记录和身份映射；
- 知识库、V2 索引和模型；
- App、安装包和当前本机自适应配置；
- Codex 登录凭证；
- 当前仍被注册表引用的客服 Codex 会话；
- 调度器活动状态和未完成发送证据。

若白名单数据不足以降至目标容量，清理器只报告“仍超限，需要人工检查”，不得扩大删除范围。

### 并发与恢复

清理器必须使用独占维护锁。自动客服正在写某个候选文件、状态文件解析失败、路径不在规范根目录、发现符号链接或文件身份在检查后发生变化时，跳过该项目。每次清理先产生候选清单，再逐项重新验证。

每次运行写入：检查时间、触发原因、清理前后容量、删除的 messageHash、释放字节数、跳过原因和错误。无清理也写入简短检查结果，供同事和 Codex 查询。

清理是永久释放磁盘空间的操作，因此安装手册必须在创建自动任务前向用户明确说明白名单范围。自动任务只运行随包安装且 SHA-256 校验通过的维护工具；维护脚本自身变化时必须重新安装并重新校验。

## 自动任务提示词合同

手册要求同事电脑上的 Codex 创建以下语义的定期任务，而不是让模型每次自由决定删除内容：

> 每天检查千牛全自动客服版本 B 的稳定维护目录，运行已安装并经过校验的“检查并安全清理”工具。不得自行编写删除命令，不得扩大工具白名单。若工具正常且无须清理，不通知用户；若完成清理，报告释放空间；若仍超过 10 GiB、状态损坏或工具失败，通知用户并附日志路径。

通知偏好与调度配置保存在自动任务本身，不写进业务 Prompt。

## 测试与验收

发布前必须完成：

1. 清理器单元测试：30 天边界、10/8 GiB阈值、最旧优先、只删 completed、状态损坏、符号链接、并发变化和幂等。
2. 临时运行根目录集成测试：构造活动与完成视频，确认活动数据字节级不变。
3. 安装器测试：从含空格和中文的路径运行，维护工具仍复制到稳定目录。
4. 手册检查：必须包含文本模式、客服名称、Gatekeeper、三项权限、接待中心、自适应、预热、开始/停止和诊断说明。
5. App 全量测试与构建通过；签名深度验证通过。
6. DMG 挂载验证、App 哈希验证、Git bundle 克隆验证、最终 ZIP 解压与全文件 SHA-256复核。
7. 确认交付包不包含运行数据和凭证。
8. 在全新临时目录从 Git bundle 恢复仓库，并使用交付手册中的命令完成至少一次测试与 App 构建，确认工程师能够继续修改。

## 发布边界

本交付仍是单 App 实例绑定一个千牛账号/一个接待中心窗口的版本 B，不把之前的双账号 SkyLight 实验混入本次发布。多账号总控另行设计和验收。
